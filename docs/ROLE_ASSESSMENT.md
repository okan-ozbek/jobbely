# Decision: opt-in AI resume alignment with a selected role

**Status:** Implemented 15 October 2026 (Europe/Amsterdam). Local Sol 6.1 compatibility checked with fictional candidate input. Independent quality calibration and production subscription/provider launch gates remain pending.

## Rationale and boundaries

Job-detail comparison offers **Assess with AI** for active Pro users with a current reviewed resume. It runs a strict screening rehearsal against stated job requirements, separating ATS keyword/qualification evidence and recruiter experience/contribution evidence. It reviews original resume text, not profile corrections, and cannot change deterministic qualification fit, coverage, ranking, candidate claims or activity tenure. The existing comparison works independently of AI availability or failure.

An employer's actual ATS configuration, knockout questions and recruiter decisions are unknown. The module reports qualitative alignment and evidence confidence, never an ATS/recruiter pass probability, hiring prediction or automatic screening decision. It does not assess file parsing. Missing resume evidence is not proof of missing ability. Advice must be reviewed and added only when factual.

## Contracts, access and privacy

[POST `/api/v1/jobs/:id/resume-assessment`](../backend/src/api/resume-review-routes.ts) accepts bounded resume text and literal `aiConsent: true`. The server resolves the job through its catalog; clients cannot replace its description or submit account/plan claims. The route shares the resume reviewer's active session, exact Origin, CSRF, server-owned unexpired Pro capability, post-work access recheck, silent logging and `no-store` controls. Missing jobs return a generic 404 before model admission. [Schemas](../backend/src/api/role-assessment-schemas.ts) own the strict contract; regenerate frontend types with `pnpm contracts`.

Resume input is limited to 40,000 characters and 2,000 lines. [The workflow](../backend/src/application/resume/review-resume.ts) omits the first nonempty resume line and obvious contact/URL/location lines. The authoritative job document is minimized similarly and capped at 24,000 characters. This is not complete anonymization. Original file bytes remain local; Jobbely does not persist candidate inputs/results. Provider/account retention controls and the development subprocess boundary remain owned by [RESUME_REVIEWER](RESUME_REVIEWER.md) and [RESUME_PRIVACY](RESUME_PRIVACY.md).

The button is explicit per-request consent with nearby OpenAI processing information. Requests never start on navigation or profile analysis. [RoleAlignmentAssessment](../frontend/src/features/resume/RoleAlignmentAssessment.tsx) binds results to job, original text and account identity. Source/profile changes, clear, identity/CSRF change, unavailable access and unmount clear or release feedback and cancel pending work. Focus and access-expiry checks refresh availability. Cancellation retains deterministic comparison. State is React memory only.

Both writing review and role assessment use the same configured [provider](../backend/src/infrastructure/resume/reviewer-factory.ts), transport limits and shared admission: five attempted AI requests/hour/account, one active/account, four/process. The local Codex adapter additionally permits one subprocess at a time across both actions. Failed/cancelled attempts count; quotas are process-local, not durable across replicas. Hosted production remains subject to the reviewer's billing, retention, isolation and budget gates.

## Evidence and confidence

[The provider contract](../backend/src/infrastructure/resume/role-contract.ts) requests two to 24 observations covering both areas and every identified material required criterion, then preferences/responsibilities. Alternatives remain one criterion; examples and employer background are not mandatory qualifications. Each row includes required/preferred/responsibility priority and an exact nonempty job quote. Supported/partial observations must also quote an exact passage at its supplied original resume line. Missing-evidence observations have null resume quote/line. A contradiction requires a quoted resume statement explicitly conflicting with the requirement. Listed keywords, total career duration and related tools cannot establish proficiency, activity-specific years or production ownership.

[Domain validation](../backend/src/domain/resume/role-assessment.ts) rejects the entire result for invented/mislocated quotes, duplicated area/job quotes, absent areas or rewrites on missing/contradicted evidence. Invalid/refused/truncated provider output returns unavailable feedback; it cannot inflate alignment by silently dropping a gap. The API adapter allows up to 8,000 completion tokens for this larger contract; writing review retains 3,000. Response/deadline/tool limits remain unchanged.

Each area shows a conservative screening result. Missing or contradicted **required** criteria produce **Required qualifications not demonstrated** regardless of supported keywords elsewhere. Partial requirements or other incomplete evidence produce **Evidence needs clarification**. Partial/shortened context or no identified required criteria withhold screening readiness. Only supported requirements with complete model-declared context can produce **Requirements appear supported**. A prominent gap message explains that wording cannot satisfy missing experience/qualifications and suggests verifying requirements or considering better-matched roles.

The application derives each area's summary from these selected observations:

- Strong overlap: at least two observations, all supported, with complete context. Partial overlap: some supported/partial evidence. Limited evidence: none supported/partial; contradiction quotes do not count as overlap.
- High evidence confidence: all observations supported, at least three distinct quoted resume lines, and complete/unshortened context. Moderate: some verified resume quotation, including explicit conflicts. Low: none. Partial/shortened context caps confidence at moderate.

These are presentation rubrics for grounded evidence, not calibrated semantic certainty or screening odds. Model-declared `all_identified` coverage is not independent proof of complete extraction; it can omit or misinterpret requirements. Exact quotes cannot prove the model's priority/status interpretation or factual advice. The result includes those limits and separates original job/resume excerpts from suggestions. Neither prompt instructions nor strict schema guarantee resistance to every instruction embedded in document text.

The shared panel now tracks pointer position for a restrained gradient glow, without tilting the form. Hover feedback is disabled for touch and reduced-motion preferences. [ProBadge](../frontend/src/components/ProBadge.tsx) owns the same subtle badge in both contexts. [ReviewProgress](../frontend/src/features/resume/ReviewProgress.tsx) replaces separate writing/role loader markup and styles with a floating AI/document symbol, softly breathing halo, orbiting dots and indeterminate strip. Each caller supplies accurate task text; cancellation and transient-state boundaries are unchanged. All new animation is pending-only and disabled by reduced motion. Suggestion panes now use the application's pearl/lavender/blue palette while retaining text labels and explicit diff markers.

The softer presentation follow-up removes the top accent bar and icon tile, using subtle lavender/blue/blush lighting and an inline sparkles icon. Both actions occupy the same header slot beside the Pro badge. The general reviewer submits its settings form through a unique native `form` association, preserving Enter submission, disabled/busy states, explicit AI consent and cancellation. Browser checks used fictional data: header click/document checks, Enter in a settings field with opted-in fake AI, cancellation and both 390px layouts passed without horizontal overflow. No live model call was needed for this presentation change.

Both actions use [ProReviewPanel](../frontend/src/features/resume/ProReviewPanel.tsx): a soft lavender/blue/blush surface, thin border, inline AI icon and Pro badge. **Pro resume reviewer** is the stable user-facing container name for annotations; `data-review-module="resume"` and `"role"` identify its two contexts. Both titles/actions include the established sparkles icon. [ResumeReviewInfo](../frontend/src/features/resume/ResumeReviewInfo.tsx) provides title-adjacent assessment limits on hover, focus or tap, with viewport clamping and keyboard/outside dismissal. The old role limits disclosure is removed.

[ResumeSuggestionDiff](../frontend/src/features/resume/ResumeSuggestionDiff.tsx) displays current resume and proposed wording side by side in both role categories and the general reviewer. The explanation follows the edit. Small screens stack the panes. No edit is automatically applied to candidate state.

Role rewrites must use quoted source vocabulary plus a small connector allowlist, preserve protected uncertainty/negation terms and numeric tokens including percent/plus modifiers, and cannot accompany missing/contradicted criteria. Unsafe added words, numbers or removed uncertainty suppress the copyable rewrite while retaining separately labeled conditional next-step guidance. This restraint prevents straightforward fabricated tool/experience additions, but is not a complete semantic equivalence proof: reordering or deleting other source words can still alter meaning. Candidates must verify suggestions. General writing review retains its existing exact provenance/new-number validation; the shared diff presentation does not strengthen that separate provider contract.

## Match presentation

The shared score component retains qualification fit and assessed/identified coverage with its unassessable count. Duplicate **About these scores** guidance, standalone gaps/check-time paragraphs and the detail comparison source disclosure are removed. On desktop the smaller **Why this result** control sits to the right of metrics; expanded evidence fills the row. It moves below them on narrow screens. Original employer/application links and recommendation availability gates remain.

The legend uses rounded **Full match 100%** and **Partial or uncertain 25%** chips. Zero-credit purple/red legend entries are omitted. Actual purple/red evidence, questions, description highlights and zero-credit scoring remain. [MATCHING](MATCHING.md#color-weighted-qualification-fit-9-october-2026) and [SKILL_RELATIONS](SKILL_RELATIONS.md) own those policies.
